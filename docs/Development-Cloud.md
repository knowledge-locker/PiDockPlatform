The development portal is https://pidock-dev.knowledgelocker.ai, hosted on `knowledgelocker-dev` through the PRX3MUS host agent. Production is separate and unchanged. This is the engineering preview, not a production security release.

## Development certificate policy

`tools/prepare-development-certificates.py` creates independent development identity material on the Linux host after storage preparation. It refuses existing or partial material, never overwrites an identity, checks certificate purposes and installs restrictive ownership/modes. It does not change any OS trust store.

This preview uses a dedicated development self-signed CA with a one-year lifetime and no subordinate CAs. Its file-backed enrollment signer remains online only in development. Broker and ingestion-worker certificates last 90 days, expiring **2027-02-09 UTC**; the CA expires **2027-11-11 UTC**. Devices receive client-only certificates for at most 90 days. The broker certificate covers both advertised DNS names. The worker identity is `pidock-ingest` and receives only telemetry subscription and receipt publication permissions. Legacy manual preview device ACLs are excluded from this hosted broker.

CA SHA-256 certificate fingerprint:

```
96:36:33:7B:58:A2:73:8C:19:33:D1:86:69:68:31:77:FD:D7:DF:0E:45:64:AD:34:EB:56:12:16:3D:F0:3D:7B
```

Certificate identity files live beneath `/etc/pidock/development/secrets/{mqtt,enrollment}` and are included in encrypted backups. The broker key belongs to UID 1883; the worker and issuer keys belong to UID 1654. The shared public CA is readable by those two service identities. Keys are not embedded in images, release metadata, source control or this guide.

There is no automatic private-PKI renewal or working certificate revocation/disconnect yet. Arrange renewal before the dates above; do not replace the CA silently, because existing devices pin its trust. Isolated constrained signing, renewal and revocation remain production gates. Caddy's public HTTPS renewal is independent of MQTT PKI. See [Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https) and [Mosquitto certificate/ACL documentation](https://mosquitto.org/man/mosquitto-conf-5.html).

## Private owner setup

No default cloud account is created. From your own trusted terminal on the operator Mac:

```sh
ssh -t knowledgelocker-dev /opt/pidock/commission-development-cloud.sh
```

Choose your username and a password of at least 14 characters; use tenant `local` and role `Owner`. Add the displayed setup secret to your external authenticator as a time-based account, then enter two consecutive six-digit codes generated by that authenticator. Invalid or expired codes allow up to three attempts per step without changing the setup secret. If setup aborts, a new run generates a new secret; use the authenticator entry for that new secret. The default algorithm is time-based SHA-1, six digits, with 30-second intervals. Keep that terminal private. Do not paste passwords or setup secrets into chat, logs or source control.

The helper takes the storage maintenance lock, briefly stops the serving cloud process, commissions through a network-isolated temporary container using the deployed image and retained volume, and restarts the cloud when it exits. Docker logging is disabled for the setup container so the displayed authenticator secret is not recorded in its container log. No account-reset endpoint is introduced. The broker stays running. If interrupted, review any remaining setup container locally before retrying; do not run simultaneous setup processes.

After setup, sign in at the portal and use **Add device**. On PiDockOS, enter this HTTPS origin and the single-use code under **Cloud connection**. Its response supplies the MQTT trust certificate and hostname; never bypass TLS validation. A battery-free Pi must have correct network time for OTP and certificate validation.

## Acceptance and operations

The pre-commissioning `tools/verify-hosted-development.py` is deliberately restricted to the named development host before any account exists. It briefly stops the cloud to seed one isolated diagnostic invitation, redeems it through public trusted HTTPS, checks cross-tenant MQTT rejection, sends a sample through certificate-authenticated MQTT, checks its persisted state and receipt, then removes its diagnostic registration, history and key and restarts the cloud. The Mosquitto 2.0 client can report a denied PUBACK while returning exit status zero; the check uses the explicit Not authorized reason. Once accounts exist, test through normal authenticated enrollment instead.

Verified on 2026-11-11: public HTTPS trust/health and unauthenticated dashboard protection; HTTPS device issuance; private cloud-to-broker TLS; cross-tenant publication rejection; durable telemetry receipt; diagnostic cleanup and retained service state. An external check from the operator Mac also passed after the development-only IPv4 TCP 8883 firewall rule was saved.

Back up both services in a coordinated stop, retain an encrypted off-host recovery copy, then restart them. Owner commissioning changes the account/key state, so take another offline backup afterward. Automatic off-site scheduling remains pending. See [Persistent storage](Persistent-Storage.md).
