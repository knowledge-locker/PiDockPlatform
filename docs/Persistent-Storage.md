# Persistent PiDockCloud storage

PiDockCloud state belongs to the host, independently of its replaceable container. Each environment has two external Docker volumes:

| Environment | Cloud state (UID/GID 1654, mode 0700) | Broker state (UID/GID 1883, mode 0700) |
| --- | --- | --- |
| Development | `pidock-development-cloud` | `pidock-development-broker` |
| Production | `pidock-production-cloud` | `pidock-production-broker` |

Cloud state mounts at `/var/lib/pidock`: accounts, the Data Protection key ring needed to decrypt them, fleet registrations, invitations and telemetry. Broker state mounts at `/mosquitto/data`. Docker labels identify PiDock ownership, environment and role. Preparation rejects unfamiliar labels, nonlocal drivers, driver options, unexpected host paths and unsafe existing permissions. It never adopts an unrelated volume or clears existing state.

Secrets live outside images and volumes at `/etc/pidock/<environment>/secrets`. Individual files mount read-only. Supply `mqtt/ca.crt`, `mqtt/worker.crt`, `mqtt/worker.key`, `enrollment/issuer.crt`, `enrollment/issuer.key` for the cloud; the broker additionally needs `mqtt/broker.crt` and `mqtt/broker.key`. Files must be readable by their assigned service UID, must not be group-writable or accessible to other users, and must not use symlinks. Keep signing keys private; isolated issuance remains a production requirement. No keys or user accounts are generated by the storage preparation command.

## Host preparation

Install Docker and restic from maintained repositories. Copy `tools/cloud-storage.py` to `/opt/pidock/cloud-storage.py`, then run as root on each Linux host:

```sh
python3 /opt/pidock/cloud-storage.py prepare --environment development
python3 /opt/pidock/cloud-storage.py status --environment development
```

Use `production` on the production host. Preparation is repeatable and preserves existing configuration and backup passwords. It creates owner-only backup administration paths, separate random recovery passwords and an encrypted restic repository. On a PRX3MUS host, its privileged agent receives directory traversal for validation and access to the runtime configuration, not general access to secret contents.

## PRX3MUS integration

PRX3MUS host agents now support operator-controlled `Agent:ApplicationRuntimeProfiles`, loaded from a protected file named by `Agent__RuntimeProfilesFile`. The PiDock profiles in `deploy/prx3mus/` bind catalog application `github-1454229394` to its exact approved image repository, environment hostname, non-root user, labelled cloud volume and five read-only secret files. Deployment requests cannot supply arbitrary host paths or extra Docker options.

Install the corresponding profile into `/etc/prox3mus-agent/runtime-profiles.json` and configure `/etc/pidock/<environment>/configuration/prx-runtime.env` from its example. Set the exact trusted Caddy source address before installation. The examples deliberately leave MQTT disabled until its separately operated broker, private connectivity and credentials are ready. Missing secret files block PiDock installation without disabling other applications or the agent.

Profiled workloads use a read-only container root, dropped capabilities, no privilege escalation, a temporary `/tmp`, process limits and a 512 MiB memory limit. Before replacement, the agent validates the host files and volume labels and rejects another active consumer. It stops the old writer before creating the replacement. On failure it restarts the old container only after confirming the failed candidate was removed. Volumes are retained through replacement and rollback; the agent never deletes them. This is a single-host, single-writer design; it does not implement distributed locking or concurrent cloud replicas.

The PRX3MUS implementation lives in the separate private source tree `~/Sites/Prox3mus_com`; it is not included in PiDockPlatform's public repository. Its host deployment documentation is `deploy/persistent-app-storage.md` in that tree.

`deploy/compose.host.yaml` provides an alternative explicit self-hosted contract using the same external volumes. It binds HTTP and MQTT only to loopback, requires existing certificate files and uses the broker ACL from this repository. A verified HTTPS proxy and a deliberate device-reachable MQTT TLS route are required before enrollment. Do not run Compose and PRX3MUS as simultaneous managers of the same cloud volume.

## Backups and recovery

As root, stop both PiDockCloud and its broker in a coordinated maintenance window, then run:

```sh
python3 /opt/pidock/cloud-storage.py backup --environment development
python3 /opt/pidock/cloud-storage.py check --environment development
python3 /opt/pidock/cloud-storage.py restore-test --environment development
```

The helper refuses active volume consumers; it does not stop services automatically. It backs up both volumes, secrets and runtime configuration. An inventory records file hashes, ownership and permissions. `check` reads the encrypted backup data. `restore-test` restores into a separate private staging directory, verifies the inventory and removes that staging copy. It never overwrites live storage. Keep services stopped throughout the backup; the pre/post consumer checks do not replace operator coordination.

The repository is `/var/backups/pidock/<environment>/repository`; its recovery password is `/etc/pidock/<environment>/backup-password`. Retain both in protected off-host recovery storage. Loss of the password prevents recovery; exposure of the password together with the repository exposes saved credentials and keys. Do not commit either to source control. Restore the key ring together with accounts; an empty replacement key ring cannot decrypt existing accounts.

Recovery into service remains an operator procedure: stop all writers, preserve the current state, restore a selected verified snapshot into staging, check its hashes and permissions, then copy the corresponding data and secrets into the designated inactive volumes and paths. Check authentication, device registrations and MQTT after restart. The helper intentionally has no command that overwrites live production data or deletes production volumes.

There is no automatic backup schedule, off-site replication job or retention/pruning policy yet. Repository growth and the age of the last successful off-host copy require operator monitoring. Do not schedule this offline backup against running JSON writers or silently delete snapshots. The appliance telemetry purge policy does not apply to cloud recovery backups.

## Verified deployment status (2026-11-11)

Both hosting servers have their separate volumes, encrypted backup repositories and storage-capable PRX3MUS agents. Authenticated agent capability checks report one runtime profile on each host. Agent replacement preserved all pre-existing running application container IDs. Previous binaries and configuration are retained in protected host-local rollback directories.

Disposable checks on both hosts validated fresh-container retention, account decryption/authentication with the retained key ring, registration/fleet/telemetry retention, rejection of backups with active writers, encrypted data checks and recovery into staging. The development host additionally exercised two real deployments through the new agent deployment code, including a readable read-only secret mount and retained state. The private PRX3MUS suite passed all eight groups, including rollback and profile rejection cases.

A protected off-host copy of each encrypted repository and its recovery password is retained on the operator Mac under the ignored `.state/cloud-recovery/` directory. These are baseline backups of currently uncommissioned cloud storage; they are not evidence of a running hosted PiDockCloud service. The development portal, broker, certificates and public connectivity are now configured; see [Hosted development](Development-Cloud.md). The development cloud owner and first Pi have been commissioned. Production remains uninstalled.

For repeatable disposable verification, publish `tools/PiDock.Storage.Verify` to `/opt/pidock/storage-verifier` and run `tools/verify-cloud-storage.py` as root on a Linux Docker host. It creates only `test-<id>` storage instances, checks real .NET account/key/registration persistence, backup and restore, then removes its test storage. Optional `PIDOCK_VERIFY_PRX_AGENT=1` additionally requires the private PRX3MUS verification executable at `/opt/pidock/Prox3mus.AgentVerification`; it uses an isolated proxy stub and no public route.
